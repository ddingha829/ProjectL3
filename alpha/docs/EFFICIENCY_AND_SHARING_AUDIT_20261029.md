# 티끌 저장·조회·로딩 점검 및 공유 흐름 수정

## 실제 서비스 읽기 전용 점검

2026-10-29, 현재 ticgle.kr의 백엔드와 로컬 연결 주소가 동일한 것을 확인한 뒤 집계했다. 실제 기록·계정·파일은 수정하거나 삭제하지 않았다.

| 항목 | 확인값 |
| --- | --- |
| 통합판 기록 | 5개 |
| 프로필 / 모임 | 3개 / 2개 |
| Storage 사진 | 2개, 합계 450,988 bytes (약 440KB) |
| 최대 사진 | 232,340 bytes |
| 300KB 초과 / WebP가 아닌 사진 | 0개 / 0개 |
| 참조되지 않는 사진 | 0개 |
| 기록 payload JSON 합계 | 3,911 bytes |
| DB에 포함된 data URL 사진 | 0개 |

payload JSON 크기는 DB의 물리적 사용량이 아니다. 인덱스·행·인증·로그·시스템 영역의 용량과 과거 egress/CPU 통계는 이번 Storage/Data API 집계에 포함되지 않는다. 원본 사진 크기를 저장하지 않으므로 원본 대비 압축률을 추정해 보고하지 않는다.

## 유지하는 절약 장치

- 업로드 전 최대 1080×2160, 300KB 이하 WebP 압축. 브라우저 인코더가 WebP를 지원하지 않으면 필요한 시점에 WASM 코덱을 불러온다. 압축 실패 시 원본을 그대로 올리지 않는다. Storage 버킷도 300KB/WebP 제한을 적용한다.
- DB에는 사진 경로만 저장한다. 작품 포스터는 외부 이미지 프록시 참조를 사용하고, 카드 디자인은 설정값으로 렌더링하므로 모임에 공유할 때 사진 원본이 복제되지 않는다.
- 피드는 서버 쿼리에서 4개씩 커서 조회한다. 검색은 300ms 지연하고 필터·정렬은 서버에서 적용한다. 같은 페이지의 연관 데이터는 묶음 조회한다.
- 기록은 변경 작업을 RPC 트랜잭션으로 저장한다. 작업 ID로 재시도의 중복 쓰기를 막고 revision으로 충돌을 검출한다. 예전 데이터를 위한 테이블이나 Storage 파일을 임의로 정리하지 않는다.
- 지도는 필요한 화면에서 로딩하며, 전국 행정동 데이터를 항상 다운로드하지 않는다. 장소에 해당하는 경계와 시·군·구 경계가 메모리에 캐시된다. 작품 검색·소개 요약의 서버 캐시와 사용량 제한도 유지한다.
- private 응답/사진은 Service Worker에 영구 저장하지 않는다. 정적 JS는 immutable 캐시를 사용한다.

## 이번 개선

1. 사진별 `createSignedUrl` N회 요청을 최대 100장씩 `createSignedUrls` 묶음 요청으로 교체했다. 계정·클라이언트별 메모리 캐시로 20초 내 동일 주소와 진행 중 요청을 공유한다. 캐시는 최대 600개이며 URL 권한은 기존 60초를 유지한다.
2. 실시간 연결이 SUBSCRIBED 상태인 동안의 정기 DB 보정 조회를 30초에서 5분으로 조정했다. 연결이 비정상이면 기존 30초 조회를 유지한다. 실시간 변경·복귀·온라인 전환 시에는 즉시 조회한다. 집중/복귀 이벤트가 겹치면 한 요청으로 합치고, 조회 중 들어온 변경은 후속 조회로 반영한다.
3. 사진 권한 주소 갱신은 DB 전체 조회와 분리했다. 화면을 보고 있는 동안 30초 주기로 사진 주소만 묶음 갱신해, 1분 권한이 만료된 사진을 상세에서 새로 열 때 깨지는 회귀를 방지한다. 숨겨진 화면에서는 갱신하지 않는다.
4. 공유 도구와 백업 코드는 실제 해당 기능을 열 때 불러오도록 분리했다. 공유 이미지 형태별 결과도 열린 창 안에서 재사용한다. 초기 JS 총량 감소율은 확인되지 않았으므로 수치로 주장하지 않는다.

실시간 연결이 안정적인 무변경 화면에서는 정기 DB 조회가 시간당 120회에서 12회로 줄어든다. 이는 정기 보정 조회만 계산한 값이며 사진 권한 갱신·실시간 변경·사용자 조작 요청까지 포함한 전체 트래픽의 90% 감소를 뜻하지 않는다.

## 피드·카카오톡 공유

- 피드 검색 버튼을 왼쪽으로 옮기고 카테고리를 오른쪽 도구 묶음에 배치했다. 카테고리 팝오버는 툴바 기준으로 정렬해 작은 화면 밖으로 넘치지 않게 했다.
- 공유를 열면 먼저 앞면 1장·앞뒤 2장·합본 1장 또는 뒷면 전체를 선택한다. 선택은 이미지 준비만 수행하며 자동 다운로드나 업로드를 하지 않는다. 이후 카카오톡·기기 공유·이미지 저장을 선택한다.
- 카카오 업로드 응답의 HTTP 이미지 주소는 허용된 카카오 이미지 호스트인지 검사하고 HTTPS로 정규화한다. 공개 이미지 뷰어의 HTTPS/호스트 제한은 유지한다. 업로드 이후 주소 검사 단계에서 발생한 오류의 재현 입력을 테스트했다. 카카오톡 실제 대화방 전송은 자동 실행하지 않는다.

일차 문서: [Supabase batch signed URLs](https://supabase.com/docs/reference/javascript/storage-from-createsignedurls), [Storage CDN 및 브라우저 캐시](https://supabase.com/docs/guides/storage/cdn/smart-cdn), [Kakao 이미지 업로드](https://developers.kakao.com/docs/ko/kakaotalk-share/js-link#upload-image).

## 검증

- 읽기 전용 실제 사진 2장: 서명 API 1회, 즉시 반복 조회 추가 요청 0회.
- 임시 QA 계정에서 실제 서버 4/4/4/0 페이지 조회, 중복 없음, 검색/필터 및 익명 비공개 접근 차단 확인. 생성한 QA 계정·모임·기록은 종료 후 제거했다.
- 효율 회귀 13개, 카카오 업로드→템플릿 회귀 17개와 기존 공유·초대 회귀 15개, 공유 이미지 URL 제한 10개, 피드 페이지 회귀 20개, 격리 DB/RLS/트랜잭션 회귀 49개 통과. TypeScript 및 프로덕션 빌드 통과.
- 393×793 및 320×568 브라우저에서 검색 펼침·카테고리 팝오버, 공유 형태 선택, 앞면 PNG 저장, 앞뒤/합본 준비를 확인했다. 실제 iPhone 수신 대화방 결과는 별도 알파 확인 대상이다.

## 기록 증가 전에 남는 과제

- 지도·캘린더·끌렉션의 공통 snapshot은 현재 최신 300개를 상한으로 불러온다. 현재 5개 규모에서는 문제가 없지만, 수백 개 이상으로 확대하기 전에는 좌표·작품·개수만 읽는 경량 조회와 별도 전체 백업 조회가 필요하다. 이 상한을 단순 제거해 모든 본문을 무제한 내려받게 하지는 않았다.
- 사진 교체·삭제 뒤 남는 Storage 파일의 장기 정리 정책은 별도 필요하다. 현재 미참조 파일은 0개이며, 원본 확인 없이 기존 파일을 삭제하는 정리는 실행하지 않았다.
- 카테고리/검색 규모가 커지면 쿼리 실행 계획을 측정하고 복합/검색 인덱스를 추가한다. 현재 인덱스 정의 검토만으로 실제 DB CPU/쿼리 지연이 최적이라고 단정하지 않는다.
