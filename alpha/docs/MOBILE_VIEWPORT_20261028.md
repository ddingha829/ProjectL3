# 모바일 헤더·리모콘 공통 프레임

현재 구현은 맨 아래 **첨부 화면 확인 후 높이 기준 수정** 절을 따른다. 앞부분은 이전 조정의 검증 기록이다.

## 문제와 확인 범위

설치형 iPhone에서 짧은 타일·지도·스튜디오 화면의 리모콘이 긴 피드보다 위에 표시됐다. 이전 구현은 헤더와 리모콘을 각각 `fixed`로 배치했지만, 페이지 전체가 문서 스크롤을 소유하고 `bottom`은 WebKit의 고정 위치 보정에 의존했다. `fixed` 속성과 body 포털만으로 화면 간 차이를 막지 못했다.

헤더의 CSS `filter`와 `backdrop-filter`는 이미 `none`이었다. 스크린샷의 상단 일부 흐림은 설치 웹앱의 상태 표시줄 합성 효과와 겹치는 것으로 판단했다. Windows의 브라우저에서는 iPhone 시스템 효과 자체를 재현하지 못하므로 이 원인 판단과 실기기 확인은 구분한다.

## 변경

- `UnifiedChrome`이 헤더와 리모콘을 하나의 body 포털 프레임에 배치한다. 프레임은 visualViewport의 top·height를 사용하고 리모콘은 그 안에서 절대 위치로 배치한다. 화면 콘텐츠 높이와 문서의 bottom-fixed 보정을 사용하지 않는다.
- 로그인한 앱의 문서 스크롤을 잠그고 `[data-app-scroll]` 콘텐츠 창만 스크롤한다. 로그인·로그아웃 시 잠금은 해제한다. 지도, 타일, 스튜디오는 같은 남은 화면 높이로 계산한다.
- 설치형 iOS 세로 화면은 하드웨어 safe area 외에 12px 여유를 두어 헤더 글자가 시스템 가장자리 효과와 겹치지 않도록 한다. 일반 브라우저·가로 화면에는 추가하지 않는다. 앱 헤더와 전체 프레임에는 블러를 적용하지 않고 리모콘 알약의 글래스 효과를 유지한다.
- 카드 뒤로가기·탭 전환·사용 가이드의 스크롤 복원을 실제 콘텐츠 창으로 옮겼다. 피드 검색 메뉴의 sticky 판단도 콘텐츠 창의 좌표를 기준으로 바꿨다.

## 하단 위치 후속 조정

사용자가 이전 공통 위치도 높다고 피드백해, 리모콘의 바닥 여백을 화면 높이의 1%(최소 6px, 최대 10px)와 남은 safe area로 계산하도록 낮췄다. 설치형 iOS의 visualViewport에서 이미 제외한 하단 inset은 다시 더하지 않는다. 키보드가 가린 영역은 이 보정에 사용하지 않는다.

지도·타일·스튜디오·캘린더와 피드 마지막 행의 여백은 동일한 리모콘 점유 높이와 10~16px의 콘텐츠 간격을 공유한다. 짧은 휴대폰에서는 타일 안내를 한 줄로 줄여 보드와 팔레트를 위한 공간을 확보한다.

- 390×844: 네비게이션 bottom 835.56 (바닥 여백 8.44), 이전 828보다 하단에 배치. 스튜디오 저장 bottom 751.89 / 리모콘 top 771.56, 타일 팔레트 bottom 758.89로 겹침 없음.
- 320×568: 바닥 여백 6px, 스튜디오 저장 bottom 481 / 리모콘 top 498. 타일 소개를 압축해 4×4 보드와 팔레트를 한 화면에 배치.
- 768×1024: 바닥 여백 10px. 스튜디오와 지도 콘텐츠가 동일한 하단 기준을 사용.
- `test:viewport` 15개 통과. 추가 검사는 하단 inset 중복 방지와 키보드 영역 구분을 다룬다. 실제 iPhone의 시스템 합성 효과는 별도 실기기 확인 대상이다.

## 첨부 화면 확인 후 높이 기준 수정

사용자가 보내준 피드와 지도 이미지에서 두 메뉴의 리모콘 위치는 같지만, 홈 표시줄 위로 큰 빈 영역이 함께 남는 것을 확인했다. 앱 프레임 높이를 `visualViewport.height`로 고정한 부분을 제거했다. 정상 화면은 CSS `position:fixed; inset:0; height:auto`로 브라우저의 상·하단에 맞춘다. 본문 안의 지도·타일·스튜디오·캘린더는 실제 콘텐츠 컨테이너의 `cqh`로 맞춘다.

visualViewport 높이를 앱 크기로 사용하는 경우는 텍스트 입력에 포커스가 있고 키보드로 시각적 영역이 줄어들었을 때로 제한한다. 입력 종료 시 측정값 회복이 늦어도 정상 고정 기준으로 복귀한다. 공통 프레임의 ResizeObserver는 CSS로 배치된 실제 크기를 읽어 설정창·카드 팝업에도 공유한다. 하단 safe area를 한 번 적용하며 임시 중복 보정은 제거했다.

- 로컬 회귀 화면에서 실제 높이 844px를 유지하고 측정값만 844 → 760px로 변경: 공통 프레임 bottom 844, 리모콘 bottom 836 유지. 이전 높이 고정 방식에서는 리모콘이 측정값을 따라 올라가는 조건이다. 검증용 경로는 빌드 전에 삭제했다.
- 실제 앱 390×844 브라우저에서 피드·지도·타일·스튜디오 모두 프레임 bottom 844 / 리모콘 bottom 836 확인. 타일/지도 콘텐츠 bottom 759.34, 스튜디오 저장 bottom 752.34로 겹침 없음.
- 위치·키보드/포커스 회귀 15개, 문제 보고서 7개 검사 통과. 문제 보고서에는 사용자가 직접 복사할 때만 화면·뷰포트·프레임·리모콘 좌표를 포함한다. 계정·로그·GPS를 자동 첨부하거나 서버로 전송하지 않는다.

설치 iPhone의 실제 WebKit 합성 결과를 데스크톱 브라우저 검증으로 단정하지 않는다. 계속될 경우 보고서의 버전과 위치 수치로 정상 CSS 영역 자체가 제한되는지 구분한다. 관련 보고: https://www2.webkit.org/show_bug.cgi?id=313800

## 실기기 보고: 59px 영역 차이와 설치 설정 비교

사용자가 `alpha-f2b2f8d`, iPhone 홈 화면 설치 앱에서 보내준 값:

```
screen=852; layout=793; visual=793; visualTop=0
frameBottom=793; dockBottom=759; dockInset=34
Safari Version/27.0.1; width=393
```

앱의 CSS 프레임도 793px에서 끝나며 화면과 59px 차이가 난다. 최신 버전이 실행 중이므로 이전 번들만의 문제는 아니다. 화면 밖 시스템 영역을 `screen.height`로 억지로 늘려 UI를 잘라내는 보정은 하지 않는다. 설치 시점에 저장된 시스템 UI 설정과 현재 WebKit 영역을 구분할 필요가 있다.

`/viewport-install/`에 병렬 설치 안내, `/viewport-install/app/`에 동일한 `UnifiedApp`을 준비했다. 이 경로는 deprecated 상태표시줄 스타일 태그를 생성하지 않으며, 별도 manifest ID `/viewport-install/v1`과 이름 `화면 테스트`를 쓴다. 기존 아이콘은 그대로 둔 채 Safari에서 새 아이콘을 추가해 비교한다. 실기기 결과가 오기 전에는 해결됐다고 판단하지 않는다.

Next의 루트 file-based manifest는 자식 레이아웃의 manifest 선택보다 우선하므로, 기존 `/manifest.webmanifest`를 동일 내용의 명시적 Route Handler로 제공하도록 옮겼다. 기존 manifest의 URL/ID/이름/시작 URL/범위/아이콘을 포함한 JSON 전체가 수정 전과 같음을 검사했다. 원래 앱의 상태표시줄 설정·UI·인증·DB는 이 비교 실험에서 바꾸지 않았다.

검증: `node scripts/test-viewport-install.mjs` 로컬 프로덕션 HTTP 검사 11개 통과. 두 페이지의 legacy 스타일 태그 부재, capable 태그, 독립 manifest 선택, MIME/ID/start URL/scope/display, 기존 manifest 동일성을 확인했다. 390px 안내 화면 가로 넘침 없음, 테스트 실행 경로에서도 동일한 설치 설정 유지 확인.

현재 WebKit 개발자의 deprecated 키 제거 안내와 설치 시점 보고: https://www2.webkit.org/show_bug.cgi?id=317153
복수 설치 및 Manifest ID: https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/

## 카드가 가려지지 않는 원래 피드 기준으로 하단 배치 조정

사용자가 재설치 비교보다 기존 피드에서 카드가 가려지지 않던 낮은 위치를 요청한 점을 다시 확인했다. 공통 프레임은 유지하고 다음 두 가지를 함께 수정했다.

- 설치형 iOS 세로 화면에서 화면 너비가 CSS 너비와 일치하고, 키보드/확대가 없으며, 화면과 레이아웃 높이 차이가 0~100px인 경우에만 그 차이를 추가 하단 safe-area 여백에서 차감한다. 앱 프레임 자체를 늘리거나 화면 밖으로 컨트롤을 옮기지 않는다. 다른 환경에서는 기존 하드웨어 safe area를 유지한다. 기본 간격은 화면 높이의 1%, 최소 6px~최대 10px이다. 보고된 393×793 / screen 852 / inset 34 조건에서는 dock inset이 34px에서 약 7.93px로 줄어 약 26px 낮아진다. 남는 OS 영역을 복구했다고 주장하지 않는다.
- 본문 스크롤 영역의 하단을 `리모콘 높이 + 하단 간격 + 콘텐츠 간격` 위로 올렸다. 기존처럼 전체 화면 높이에 padding만 더하면 중간 스크롤 상태의 카드가 리모콘 뒤에 보이므로, 실제 scrollport의 경계를 제한한다. 카드 크기·가로 폭은 바꾸지 않았다. 지도·타일·스튜디오·캘린더는 같은 본문 컨테이너 높이를 기준으로 맞춰진다.

검증:
- viewport 회귀 18개 및 화면 스와이프 회귀 통과, 프로덕션 빌드 성공.
- 393×793 브라우저: 피드·지도·타일·스튜디오 dock top 721.08 / bottom 785.08, 본문 bottom 709.19로 동일. 지도/타일 bottom 709.19, 스튜디오 저장 bottom 708.19. 가로 넘침 없음.
- 393×660 브라우저: 피드 최대 스크롤 90px에서 마지막 카드 bottom 579 / 본문 bottom 579.41 / dock top 589.41로 카드가 가려지지 않음.
- 320×568 브라우저: dock top 498 / bottom 562, 본문 및 타일 팔레트 bottom 488, 스튜디오 저장 bottom 487로 겹침 없음.

위 브라우저 검증과 보고된 기하 조건의 훅 회귀 검사는 실제 설치 iPhone의 최종 위치 검증과 구별한다. 이번 변경은 기존 앱 주소에 반영하며 새 설치를 전제로 하지 않는다.

## 흰 사각형 회귀 제거 및 고정 레이어 구조 교체

다음 사용자 캡처에서 9ad5f06의 본문 scrollport 제한이 카드 하단을 잘라 넓은 흰 사각형처럼 보이는 회귀를 확인했다. 이 제한을 되돌리고 본문이 화면 하단까지 그려지도록 복구했다. 마지막 카드 전체를 리모콘 위로 스크롤할 공간은 본문 하단 padding으로 확보한다. 리모콘 프레임 자체는 투명하며 버튼 사이 공간은 본문을 터치할 수 있다.

높이 문제는 safe-area 차감만으로 해결되지 않았으므로 `body → 앱 → chrome`의 fixed 레이어를 제거했다. 문서는 `100dvh` 높이의 relative 캔버스이며 앱과 chrome은 그 안의 absolute 레이어로 둔다. 실제 스크롤은 본문만 소유하므로 화면 전환과 본문 스크롤로 리모콘 위치가 달라지지 않는다. 화면 물리 높이를 강제로 CSS 높이로 지정하지 않는다. 프레임 ResizeObserver는 하나의 viewport 측정 함수에 이벤트를 전달해 overlay 높이와 하단 inset을 함께 갱신한다. CSS 캔버스가 fixed-position 측정치보다 큰 경우에는 safe-area를 중복 차감하지 않는 회귀를 추가했다.

메인 경로에서도 legacy `apple-mobile-web-app-status-bar-style` 태그를 제거하고 capable/title만 유지했다. manifest ID와 기존 설치 데이터는 변경하지 않는다. 설치 메타가 이미 저장된 아이폰에서 어느 정도 반영되는지는 별도 실기기 확인이 필요하다. 관련 WebKit 개발자 안내: https://www2.webkit.org/show_bug.cgi?id=317153 (이 이슈는 FIXED 상태이며 현재 사용자 기기의 동일 원인임을 확정한 것은 아님).

사용자가 가로폭도 줄여 달라고 요청해 전체 dock 폭을 393px 화면에서 361 → 345px, + 버튼을 54 → 50px, 버튼 사이 간격을 10 → 8px로 축소했다. 320px 화면에서는 전체 288px, + 48px, 각 메뉴 54.5×50px로 최소 터치 영역을 유지한다.

검증:
- viewport 회귀 20개, 화면 스와이프 회귀, 프로덕션 빌드, 설치 메타 HTTP 검사 11개 통과.
- 393×660: chrome background 투명, body relative, 본문 bottom 660. 버튼 사이 좌표의 `elementFromPoint`가 실제 카드에 도달함. 최대 스크롤 90px에서 마지막 카드 bottom 579 / dock top 589.41로 전체 노출.
- 393×793: 지도·타일·스튜디오 dock bottom 785.08 동일, 지도/팔레트 bottom 709.19, 저장 bottom 708.19. 이 브라우저에서 기존 높이와 차이가 없는 것은 iOS 고정 레이어 차이가 재현되지 않기 때문이며, 실기기 해결 증거로 사용하지 않는다.
- 320×568: 가로 넘침 없음, + 48×48 / 메뉴 54.5×50, 저장 bottom 487 / dock top 498. 설정 본문 scrollTop 679(최하단)까지 이동 후 재진입 시 0, 문서 scrollY 0.

흰 사각형과 가로폭 변경은 브라우저에서 검증했다. 아이폰 설치 앱의 최종 하단 위치는 아직 검증되지 않았다.

## 실기기 확인 후 미세 위치 조정

사용자가 앱을 새로 실행한 뒤 하단 위치가 정상임을 확인했다. 해당 배치를 기준으로 유지하고, 후속 요청인 “조금만 더 높여줘”에 따라 공통 하단 inset에 6px만 더했다. 리모콘과 + 버튼이 함께 올라가며 피드 마지막 행 padding과 지도·타일·스튜디오의 여유 공간도 같은 토큰으로 조정된다. 화면 높이·설치 설정·폭은 변경하지 않았다.

## 입력 중 리모콘 숨김 (2026-10-29)

화면 키보드가 열린 기존 `data-lab-keyboard=open` 상태에서는 공통 리모콘 전체를 `display:none`으로 숨긴다. + 버튼과 네 개 메뉴를 함께 제거하며, 터치·키보드 포커스·접근성 트리에도 남지 않는다. 키보드가 닫히면 원래 하단 위치로 복귀한다. 화면 높이·하단 inset·본문 배치 계산은 바꾸지 않는다.

입력 포커스만으로 키보드를 추측하는 새 로직을 추가하지 않았다. 기존 text focus + visualViewport 축소 판정을 재사용하므로 데스크톱의 키보드 없는 검색 포커스는 리모콘을 숨기지 않는다. 입력에 포커스를 유지한 채 키보드만 닫는 경우, 슬라이더와 오래된 viewport 값의 조합, textarea 작성·수정의 상태 전환을 추가 검증했다. viewport 회귀 23개와 피드 툴바 회귀 14개 통과. 실제 iPhone 키보드 표시 결과는 별도 확인 대상이다.
