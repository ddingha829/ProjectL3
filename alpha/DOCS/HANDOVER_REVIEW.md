## 1. 판단 요약

## 3. 먼저 해결할 코드상 문제

### P0 · 계정 ID와 세션을 분리

`src/lib/store/util.ts:20`은 아이디를 입력으로 계정 UUID를 결정론적으로 생성합니다. `src/lib/session.ts:10`은 쿠키 값의 UUID 형식만 검사하고 그 값을 소유자 ID로 사용합니다. 즉 계정 ID가 비밀 세션 토큰 역할까지 하고 있어, 비밀번호 검증 경로를 거치지 않는 접근을 막는 구조가 부족합니다. HttpOnly는 클라이언트가 임의의 쿠키를 보내는 것에 대한 서버 검증을 대신하지 않습니다.

권고: 검증된 인증 계층과 서버에서 검증하는 세션을 도입하고, 공개 식별자인 사용자 ID와 예측할 수 없는 세션 토큰을 분리합니다. 로그아웃·만료·세션 폐기도 함께 정의해야 합니다. [OWASP 세션 관리 지침](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)도 세션 ID의 무작위성과 서버 측 검증을 요구합니다.

또한 `hashAccountPassword`는 빠른 SHA-256을 사용하고 비밀번호 관련 값을 사용량 테이블에 저장합니다. 계정 정보를 별도 모델로 옮기고 검증된 비밀번호 인증을 사용해야 합니다. 자체 저장이 필요하다면 무작위 salt를 사용하는 Argon2id/scrypt 등으로 교체하고 기존 계정의 마이그레이션을 설계합니다. [OWASP 비밀번호 저장 지침](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)

### P0 · 동봉된 DB 정책의 사용자별 접근 제한

`supabase/schema.sql:49`부터 프로필·로그·사용량 테이블의 정책이 `for all using (true) with check (true)`로 열려 있습니다. Storage 업로드·삭제 정책에도 사용자 소유권 조건이 없습니다. 이 SQL이 그대로 적용되고 해당 역할에 테이블 권한이 있다면 API 라우트의 소유자 필터를 우회하는 직접 접근이 가능해질 수 있습니다.

로컬 환경에는 Supabase URL과 anon 키가 설정되어 있고 service-role 값은 비어 있음을 확인했습니다. **실제 운영 DB의 grants/RLS와 Vercel 환경은 조회하지 않았으므로 배포 데이터 노출이 발생했다고 단정하지 않습니다.**

권고: 인증·세션 방식부터 확정한 뒤 그 방식에 맞는 소유권 정책을 적용합니다. 서버 전용 접근을 택하면 공개 역할의 DB 접근을 제한하고 서버가 매 요청의 소유권을 검사합니다. Supabase Auth를 택하면 검증된 사용자 JWT에 기반한 RLS를 사용합니다. 단순히 service-role 키만 추가하는 것으로 이 문제가 해결되지는 않습니다. [Supabase API 키와 권한 설명](https://supabase.com/docs/guides/getting-started/api-keys)

### P1 · 로그인 전 기록 이관이 실제로 작동하지 않음

`supabaseStore.ts:436`은 이전 기록을 새 소유자로 `saveArchive`하려고 하지만, 같은 함수의 `:244`는 기존 소유자가 다르면 `null`을 반환합니다. 호출부는 이 실패를 확인하지 않습니다. `fileStore.ts:223`은 이미 DB에 있는 ID는 건너뛰므로 이전 익명 기록이 대상 계정으로 넘어가지 않습니다.

격리된 파일 저장소에서 재현한 결과: 익명 기록 2개가 남아 있는 상태로 계정 연결에 성공하지만 대상 계정 기록은 0개였습니다. 기록 삭제가 발생한 것은 아니지만 사용자에게는 ‘로그인하니 기록이 사라짐’으로 보일 수 있습니다.

권고: 검증된 익명 세션에서만 수행하는 명시적 이관 작업을 만들고, 성공 확인 후 화면과 로컬 소유자를 전환합니다. 로그 ID·그룹의 memberIds·사진 소유권·프리셋·미동기화 outbox를 함께 고려해야 합니다. 이미 로그인된 다른 계정의 기록을 자동 병합해서는 안 됩니다.

### P1 · 저장 실패를 성공으로 처리하는 폴백

`fileStore.ts:57`의 `persist`는 디스크 쓰기/rename 오류를 삼킵니다. 격리 테스트에서 쓰기를 실패시켜도 `saveArchive`가 저장된 항목을 반환했고 실제 파일에는 기록이 없었습니다. 서버가 성공을 반환하면 브라우저는 동기화 완료로 판단할 수 있으므로, 재조회·재시작에서 기록이 사라지는 위험으로 이어집니다.

또한 Supabase 오류를 파일 저장소로 넘기는 판단이 테이블명 문자열 포함 여부까지 사용하고 있어 실제 스키마 부재 이외의 오류도 숨길 수 있습니다. Vercel Functions의 임시 파일과 메모리는 영속 서버 저장소로 간주하면 안 됩니다. [Vercel의 서버리스 로컬 저장소 설명](https://vercel.com/kb/guide/is-sqlite-supported-in-vercel)

권고: 운영에서는 DB 장애를 정직한 실패/동기화 대기로 반환하고 브라우저 outbox를 유지합니다. 파일 폴백은 로컬 개발용으로 한정하며 파일 쓰기 실패도 호출자에게 전달합니다. 운영 설정 누락을 ‘모든 기능 정상’으로 표시하지 않습니다.

### P1 · 비공개 로그와 공유 링크의 경계

`/share/[id]`는 `getPublicArchive(id)`를 호출하며 두 저장소 모두 공유 허용 여부·공유 토큰·철회 상태를 검사하지 않습니다. 현재는 로그 ID를 아는 방문자가 별도의 공유 활성화 없이 열 수 있는 구조입니다. 무작위 UUID를 사용한다고 해서 명시적인 공유 권한과 동일해지는 것은 아닙니다.

Storage 역시 현재 public URL을 반환합니다. 공개 버킷에서는 파일 URL을 아는 누구나 다운로드할 수 있으므로, 개인 로그북의 기본 사진 저장 정책으로는 재검토해야 합니다. [Supabase 버킷 접근 모델](https://supabase.com/docs/guides/storage/buckets/fundamentals)

권고: 원본 로그·사진은 비공개로 보관하고 필요한 시점에 소유자에게 접근 URL을 제공합니다. 공유할 때만 별도 공유 토큰과 공개 카드 스냅샷을 만들고 ‘공유 끄기’를 제공합니다. 임시 서명 URL을 원본 `img`에 영구 저장하지 말고 객체 경로와 표시용 URL을 분리합니다.

### P2 · 공유된 카드의 모양이 내가 저장한 카드와 다름

`ShareCardViewer.tsx:24`와 `:32`는 소유자 프로필의 첫 프리셋을 기본으로 사용합니다. 저장된 `item.cardAppearance`가 공유 화면의 기준이 아닙니다. 따라서 프로필 프리셋 변경 후 예전에 공유한 카드의 모양도 달라질 수 있고, 그룹 카드도 `[item]`만 전달받아 실제 구성원을 재현하지 못합니다.

권고: 공유 카드와 OG 이미지는 저장된 카드 스냅샷을 기준으로 생성합니다. 공개 스냅샷에는 선택한 정보만 넣고, 소유자의 전체 프리셋 목록을 넘기지 않습니다. OG 고도화는 이 정책을 먼저 정한 뒤 진행해야 합니다.

### P2 · 목록 전체 로딩과 번호의 의미

Supabase 목록은 최신 500개로 제한되는데 UI에는 전체/잘림 구분이 없습니다. `renumber`와 `normalizeChronologicalNumbers`는 조회된 항목을 기준으로 번호를 다시 계산하므로, 삭제·부분 조회에서 번호가 달라집니다. 파일 저장소 격리 테스트에서 두 번째 기록은 앞 기록 삭제 후 `02 → 01`로 바뀌었습니다.

권고: 번호가 영구 로그 번호라면 저장 때 한 번 부여하고 조회 때 재계산하지 않습니다. 목록 순번이라면 고유 번호라고 설명하지 않습니다. 향후 페이지네이션을 도입할 때는 일부 페이지를 전체 서버 스냅샷으로 취급하지 않도록 로컬 병합 계약도 함께 수정해야 합니다.

## 4. Gemini의 4가지 제안에 대한 판단

| 제안 | 판단 | 권장 수정 |
|---|---|---|
| 사진 Storage 분리 · 높음 | 방향은 타당하나 이미 업로드 경로가 있음. ‘10배 빨라짐’은 측정 근거가 없음. | 공개 버킷 신설보다 실제 업로드 성공률·Base64 폴백 원인을 확인하고 비공개 객체 저장 + 썸네일 + 목록 요약 응답으로 개선. |
| 키보드 닫기 완료 버튼 · 중간 | 작고 효과적인 UX 개선. | 입력 포커스 때만 ‘완료’를 보여주고 blur로 닫기. iOS Safari/PWA, Android, 인앱 브라우저에서 긴 본문과 저장 버튼 접근성 확인. 화면 고정 때문에 커서가 가려지지 않아야 함. |
| 공유 링크 OG 고도화 · 중간 | 가치 있음. 다만 공유 권한과 저장 카드 재현이 선행되어야 함. | 먼저 비공개 기본값·공유 토큰·철회·스냅샷을 정하고 같은 스냅샷으로 공유 화면과 OG 이미지를 생성. |
| 비밀번호 변경·익명 병합 · 낮음 | 두 문제를 묶어 낮게 두면 안 됨. | 계정/세션 보강과 익명 이관은 우선 처리. 비밀번호 변경·복구 UI는 그 인증 구조 위에 추가. |

## 5. 제품 방향에 맞춘 추가 제안

후속 적용: 저장 완료·목록 안착 반응은 로컬 Alpha에 구현했습니다. 최신 적용 범위와 검증, 추가 UX 후보는 [SAVE_FEEDBACK.md](SAVE_FEEDBACK.md)를 참고하세요. 아래의 초기 검토 내용 중 구현 상태는 그 문서를 우선합니다.

1. **현재 설치·가입 우선 온보딩 유지 — 사용자 결정.** 소유자는 앱 추가와 가입을 먼저 유도하는 방향을 원합니다. 첫 로그 저장 이후로 안내를 미루자는 이전 제안은 철회합니다. 배너가 필수 메뉴를 가리지 않게 하는 배치 점검은 온보딩 시점과 별개입니다.
2. **버튼 명칭 변경은 보류 — 사용자 피드백 반영.** ‘디자인 적용’과 ‘공유·이미지 저장’은 오히려 직관성이 떨어질 수 있다는 의견이 있어 확정안이 아닙니다. 현재 카드 저장/공유 명칭을 유지하고, 저장 후 상태 피드백으로 결과를 명확히 하는 방안을 우선 검토합니다.
3. **설정은 기본값 중심으로 유지하기.** 목록 추가 정보·지도 자동 연결·애니메이션 등 토글이 늘어도 매번 사용자에게 결정하게 하지 않습니다. 좋은 기본값을 제공하고 고급 옵션은 설정에 모읍니다.
4. **‘내 취향이 쌓이는 맛’은 한 번의 완료 반응에 집중하기 — 방향에 사용자 동의.** 저장 버튼의 짧은 눌림 → 목록에 새 항목 안착 → ‘카드 보기’ 연결을 일관되게 만듭니다. 지속 애니메이션을 더 늘리기보다 저장 성공과 선택 변경의 피드백을 정교하게 다듬습니다. 구체적인 동작 조정은 후속 구현 과제이며 이번 문서 갱신만으로 적용 완료를 뜻하지 않습니다.
5. **성능 목표를 측정 가능한 값으로 두기.** 입력 가능까지의 시간, 로컬 저장 완료 시간, 첫 카드/목록 표시 시간, 업로드 전후 사진 용량, 공유 이미지 준비 시간을 측정합니다. 100/500/1,000개 기록으로 비교한 뒤 페이지네이션·가상화 도입 여부를 정합니다.
6. **복잡한 화면 상태를 기능별 훅으로 분리하기.** `page.tsx`에서 탭 스와이프, 카드 임시 디자인, 이미지 내보내기, 계정 전환을 단계적으로 분리합니다. 한 번에 재작성하지 말고 현재 동작을 보존하는 작은 변경으로 진행합니다.

권장 순서: **계정/권한 → 저장 실패·익명 이관 → 공유 공개 범위·카드 일치 → 사진/목록 성능 → 키보드·편집 마감**.
