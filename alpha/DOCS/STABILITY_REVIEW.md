# 앱 안정성 및 보안 재점검 — 2026-10-18

## 적용 상태

2026-10-18 운영 적용 및 검증 완료. 앱 보강 커밋 `524cd51`의 Vercel 배포 성공을 확인한 뒤 DB 접근 제한 SQL을 실행했다. 로컬 자동 회귀 검증과 운영의 별도 QA 계정/기록으로 확인했으며, 기존 사용자 기록은 변경하지 않았다. QA 계정·기록·사진은 검증 후 정리했고 유료 AI 호출은 하지 않았다.

## 발견한 운영 문제와 해결

- 로컬에 구성된 실제 Supabase 프로젝트에서 **공개 anon 키로 `l2_profiles`, `l2_archives`, `l2_ai_usage`의 행이 보이는 것**을 확인했다. `HEAD`, `Prefer: count=exact`, `limit=0` 요청만 사용했으며 기록 내용·계정 식별자·자격 증명을 가져오거나 출력하지 않았다. 세 응답은 HTTP 206, 익명 가시 행 존재였다.
- 점검 당시 Vercel과 로컬에는 공개용 키만 구성되어 있었으며 로컬 `SUPABASE_SERVICE_ROLE_KEY` 값도 비어 있었다. 사용자 승인과 Supabase 로그인 후 같은 프로젝트의 기존 서버 전용 Secret 키를 확인해 로컬 및 Vercel Production/Preview의 `SUPABASE_SERVICE_ROLE_KEY` Secret으로 등록했다. 키 값은 문서·Git에 기록하지 않는다.
- 서버 키 등록 → 보안 패치 배포 성공 → `supabase/security-hardening.sql` 적용 순으로 진행했다. 새 운영 저장소는 공개 anon 키를 서버 인증으로 사용하지 않는다.
- 적용 후 세 테이블의 anon HEAD 요청은 모두 **401**, 서버 키 HEAD 요청은 모두 **200**이었다. 공개 키의 `bump_l2_ai_usage` 실행도 **401**로 차단되었다. SQL Editor는 `Success. No rows returned`를 표시했다.

SQL은 테이블 데이터를 지우지 않는다. RLS를 유지하고 공개 테이블 권한·공개 사용량 RPC 실행 권한·프로젝트의 l2 사진 목록 조회/업로드/삭제 정책을 회수했다. 서버 접근과 기존 공개 사진 URL의 읽기는 유지한다. 적용 후 실제 앱의 저장/수정/삭제/사진 업로드/실행 취소/두 번째 기기 로그인까지 정상 동작을 확인했다.

## 호환성과 배포 순서

1. Supabase 관리 화면에서 해당 프로젝트의 기존 서버 전용 키를 확인하고, Vercel project-l3 Production/Preview에 `SUPABASE_SERVICE_ROLE_KEY`를 비밀 환경변수로 등록한다. 공개 `NEXT_PUBLIC_` 이름을 붙이면 안 된다.
2. 기존 기기의 로그인 정보 또는 복원 코드가 있는지 확인한다. 새 서명 쿠키 도입 시 한 차례 재로그인이 필요하다. 로컬 캐시는 이를 안내하며 보존한다.
3. 테스트를 통과한 보안 패치를 배포한다. 서명 키는 명시적 `SESSION_SECRET`(32자 이상)을 우선하고, 없으면 서버 전용 Supabase 키에서 용도를 분리해 파생한다. 서명 키를 교체하면 기존 세션은 재인증해야 한다. 배포 환경에서 두 값이 모두 없으면 취약한 쿠키로 계속하지 않고 실패한다.
4. `supabase/security-hardening.sql`을 해당 프로젝트 SQL Editor에서 실행한다.
5. 익명 DB 접근 차단, 실제 앱 로그인/동기화/사진 업로드를 재확인한다.

현재 앱 공유는 이미지와 선택적 Google 지도 주소를 전송하므로 공개 웹 기록 링크가 필요하지 않다. 기존 웹 링크는 소유자만 열 수 있게 바뀐다. 향후 공개 링크가 필요하면 명시적 공개 동의·전용 토큰·회수 기능을 별도로 설계해야 한다.

## 남은 제한과 다음 우선순위

1. 운영 DB 권한 SQL을 적용하고 공개 접근 차단을 확인했다. 앞으로 배포/스키마 변경 시 이 제한을 유지해야 한다. 앱 패치만으로 공개 anon 키의 직접 접근을 차단할 수 있는 것은 아니다.
2. 현재 자체 ID/비밀번호 로그인은 정식 Supabase Auth가 아니다. 계정별 세션 회수, 분산 로그인 시도 제한, 동시 신규 가입의 DB 고유 제약/트랜잭션, 비밀번호 재설정은 추가 설계가 필요하다. 이번 수정을 완전한 인증 체계 교체로 간주하면 안 된다.
3. 사진 버킷은 여전히 공개 URL 방식이다. SQL은 목록 조회와 무단 쓰기를 막지만 이미 아는 이미지 URL의 읽기를 막지 않는다. 비공개 버킷/서명 URL 및 미참조 파일의 지연 정리가 필요하다.
4. AI 20회는 계정/기기별 앱 요청 제한이다. 쿠키 재발급·여러 사용자·한 요청 안의 모델 재시도까지 포함한 프로젝트 전체 비용 보장은 아니다. 로그인 제한, 전체 지출 상한, 토큰 측정은 별도다.
5. 동일 계정을 여러 탭에서 동시에 오프라인 편집하거나 페이지 조회 중 다른 기기에서 삭제하는 상황은 충돌 정책이 완전하지 않다. 서버 revision/ETag와 계정별 저장 잠금을 다음 단계로 권한다.
6. 실제 iOS/Android 카카오톡 수신 화면과 외부 Google/Supabase 장애는 이번 로컬 자동 검증 범위 밖이다.
